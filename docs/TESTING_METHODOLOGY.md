# NIC Fraud Detection: Testing Methodology

This document outlines the two-pronged approach used to evaluate the NIC Scholarship Fraud Detection model. Because 99.97% of the historical dataset is "clean" (unlabeled), standard supervised testing methodologies are insufficient. We rely on the following two testing strategies:

## 1. The Standard Evaluation (`evaluate_model.py`)
This script automatically runs at the end of the `main.py` pipeline to evaluate the model against the real, unmutated dataset. It performs three crucial checks:

*   **PR-AUC vs Weak Labels:** Since we don't have true fraud labels, we evaluate how well the LightGBM classifier learned to predict the "weak labels" (the deterministic rules generated by the VAE/Rule Engine). A high PR-AUC proves the model correctly internalizes the baseline policy rules.
*   **The Ground-Truth Check:** We explicitly track the model's assigned risk scores for the **4 known, human-confirmed fraud applications** hidden in the 15,000 records. We verify if the model successfully ranks them at the very top of the risk distribution.
*   **SHAP Pruning (Attention Check):** We extract SHAP values to see exactly which features the LightGBM model used to make its decisions. Features that receive a mean absolute SHAP value of 0.000 are permanently pruned out, ensuring the model isn't bogged down by noise.

## 2. The Stress Test (`synthetic_anomaly_test.py`)
Because the real dataset is mostly clean, the model never naturally sees examples of complex, coordinated fraud (e.g., someone submitting their father's name as their own, or 15 applications coming from a single IP address). If we only test on clean data, we cannot prove the model will catch a real, novel attack.

To solve this, we use a **Synthetic Anomaly Harvester**:
1.  **Ingestion:** It loads the clean `data_for_ml_model.csv`.
2.  **Injection:** It randomly selects normal applications and injects hidden, targeted fraud vectors into them (e.g., mutating the `annual_family_income` to ₹5,000, or explicitly copying the `father_name` string into the `applicant_name` column).
3.  **Pipeline Execution:** We feed this "poisoned" dataset through the entire ML pipeline (`feature_selection.py` -> `vae_detection.py`).
4.  **Recall Measurement:** Finally, we measure whether the VAE and LightGBM models successfully flagged those specific mutated records as high-risk anomalies.

### Why the Stress Test Matters
The synthetic test is how we discover structural blind spots in the architecture. For example, it proved that early versions of the pipeline were aggressively deleting text columns, making the model completely blind to identity-matching fraud. 

In summary: `evaluate_model.py` proves the model is mathematically sound on clean data, while `synthetic_anomaly_test.py` proves it can actually catch hackers attempting novel fraud in production.
